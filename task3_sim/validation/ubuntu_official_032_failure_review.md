## 已从原始 0.3.2 源码确认的问题

1. 接收器只预先丢弃“桥接收到后在 Python 队列里超过 0.15 秒”的旧包。一个刚被桥接收到、但源发布到桥接已延迟的合法包，会在 `decode_sample` 中超过“源传输 + 接收队列”总年龄 0.15 秒，然后和未来时间、时钟异常一起触发永久故障。注入“传输 0.16 秒、队列 0.01 秒”的完整有限数据包，可复现相同异常文本。
2. SDK 无效反馈使用 `timestamp=-inf`；getter 不可用时向量也可能是 NaN。多靶循环把 `asdict(feedback)` 直接传给 `json.dumps(..., allow_nan=False)`。原生浮点值不会经过 `default=json_value`，因此一次正确的“反馈失效，停止等待”也会在写事件时变成程序异常。只使用有限零向量和 `timestamp=-inf`，即可复现此次 JSON 错误，不需要真实 SDK。
3. 后端 `_sync` 对缺失或过期反馈立即停止并抛异常；`capture` 和 `advance` 均调用它。即便修复前两项，短时缺帧也可能继续导致运行退出，缺少明确上限的安全重采过程。

## 首帧与线程的影响

0.3.2 在完成 standUp 后才创建视觉处理器、可视窗口，并在第一次 `capture` 内创建 renderer。图像时间戳忠实保留渲染前的原生发布时刻，之后还要保存首帧 PNG 并进行第一次 AprilTag 计算。首次开销可能使图像超过 0.15 秒；正确行为应是停止并重采，而不是允许旧图运动。

SDK 看门狗在没有活动控制租约时会直接返回，不保证在静止启动期间持续抽取原生队列。已审阅调用中没有确认接收器锁与 SDK 锁反序死锁。不能仅凭这两条终端信息确定首次变慢发生在 OpenGL、图像保存、AprilTag、eCAL 传输还是系统调度。

## 最小恢复方案与安全边界

- 只有完整校验后、源顺序正确、单纯超过年龄的数据包可丢弃；保留原始时刻和顺序审计。格式错误、非有限源值、未来/倒退时钟、错误发布者、原生进程终止继续立即失败。
- 图像或反馈失效即撤销开火权、清除瞄准稳定期、仅对已拥有的 SDK 控制族发送零；不得因 WAIT 进入新控制模式。
- 缺失反馈可在固定 2 秒上限内以新原生发布恢复。恢复起点及截止时刻只设置一次，不由每次重试续期；新状态仍须满足 0.15 秒年龄门槛。持续缺失明确 ERROR。
- 恢复后用观测 epoch 和截止时间淘汰旧 transport 帧，重新获取图像，重新累计稳定期。开火门禁不能等待状态恢复后继续使用旧图像，必须立即拒射。
- 在原生运行及非零控制开始前预热 renderer、AprilTag 和窗口；预热图像丢弃，不参与任务、瞄准或计分。
- 多靶日志把无效诊断中的非有限值表示为 JSON `null`，并显式保留 `valid=false` 和错误原因；不改控制对象，不重新打时间戳，不把坏源数据转换成有效反馈。
- 官方 SDK、ELF、策略、机器人模型以及任务一二、旧单靶保持不变。

上述源码故障机制可以本地复现；新的恢复策略仍须在 Ubuntu 回传本次完整归档后验证。此次两次运行尚未进入精瞄与射击，不能据此判断 PI 收敛或原生三靶得分。
