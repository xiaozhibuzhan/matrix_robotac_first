## 1. SSH 要装在哪里

SSH 用于远程登录机器人、检查配置、复制文件和查看日志。运动控制使用官方 SDK 的网络通信，相机使用 RTSP；两者不是经 SSH 传输。

在 Ubuntu 控制电脑执行：

```bash
ssh -V
```

能输出 OpenSSH 版本就无需安装。仅在找不到 `ssh` 命令时安装客户端：

```bash
sudo apt update
sudo apt install openssh-client
```

无需为“从电脑登录机器人”给电脑安装 `openssh-server`。官方设备已经提供 SSH 服务；若无法连接，先区分网络不通、端口拒绝或认证失败，不要直接改装机器人系统。

## 2. 首次建议先用机器人 Wi-Fi

连接机器人机身标签给出的 SSID 和密码，电脑无线网络使用自动分配 IP（DHCP）。官方默认机器人 Wi-Fi IP 是 `192.168.234.1`；如果设备经过修改，以设备实际地址为准。

在 Ubuntu 电脑检查：

```bash
ping -c 3 192.168.234.1
ip -4 route get 192.168.234.1
ssh firefly@192.168.234.1
```

路由输出中的 `src` 是电脑在这条连接上的 IP，记录该地址，后续必须使用实际值。官方初始用户名和密码均为 `firefly`，如交付方改过，应使用交付凭据；输入 SSH 密码时终端不显示字符是正常行为。首次连接需核对设备身份后接受主机密钥。

SSH 成功只说明远程登录可用，并不代表 SDK 控制或相机已经接通。

## 3. 分清电脑地址和机器人地址

假设机器人是 `192.168.234.1`，电脑实际 `src` 为 `192.168.234.15`，端口使用官方默认 `43988`：

| 位置 | 参数 | 此例中填写的值 |
| --- | --- | --- |
| 机器人 `/opt/export/config/sdk_config.yaml` | `target_ip` | 电脑地址 `192.168.234.15` |
| 同一配置文件 | `target_port` | 电脑 SDK 接收端口 `43988` |
| 电脑 SDK 程序 | `initRobot` 第一个参数 | 电脑地址 `192.168.234.15` |
| 电脑 SDK 程序 | `initRobot` 第二个参数 | `43988` |
| 电脑 SDK 程序 | `initRobot` 第三个参数 | 机器人地址 `192.168.234.1` |

这是地址对应关系示例，不应直接复制示例电脑 IP。可先在机器人的 SSH 会话中只读查看：

```bash
cat /opt/export/config/sdk_config.yaml
```

如确需修改，先保留原配置备份，再用设备上已有的编辑器只改这两个字段；不要删除其他字段或覆盖整份文件。官方要求修改后重启设备生效，重启前应让机器人处于稳定停放状态。若电脑 DHCP 地址改变，机器人回传地址也要同步更新，或通过正常网络设置保持电脑地址稳定。

对应 Python API 关系如下，仅用于说明参数，目前的仿真启动脚本不读取这些实物地址：

```python
app.initRobot("192.168.234.15", 43988, "192.168.234.1")
```

注意：仿真配置使用过 `44888`，官方部署示例默认是 `43988`。实物应让机器人 `target_port` 和实物程序 `local_port` 明确一致；不要混用两套端口或同时运行两个控制客户端。

## 4. 如果改用网线

官方有线默认地址为 `192.168.168.168`，该接口没有 DHCP。电脑需手动设置同网段且不冲突的地址，例如 `192.168.168.100/24`，机器人回传 `target_ip` 则填写这台电脑的有线地址。

非默认 Wi-Fi 网段还涉及机器人绑定地址 `SDK_CLIENT_IP`：

- 点足 ZSL-1：`/opt/app_launch/start_motion_control.sh`。
- 轮足 ZSL-1w：`/opt/app_launch/start_motion_control_xgw.sh`。
- 有线例子填写 `export SDK_CLIENT_IP="192.168.168.168"`，这里是机器人绑定的本机地址，不是电脑回传地址。

应在备份和核对实际型号后依官方指南修改现有文件并重启；不要复制文档中的整段启动脚本覆盖原脚本。官方记录了启动时网卡尚未获得该地址，可能导致运控绑定失败和遥控不可用的情况，因此首次联通推荐保持默认 Wi-Fi 路径。有线部署再核对网卡和服务启动时序，详见官方 FAQ。

## 5. 独立检查真实视频

在 Ubuntu 电脑上，如果缺少 `ffplay`，安装 `ffmpeg`：

```bash
sudo apt install ffmpeg
```

按默认 Wi-Fi 地址播放：

```bash
ffplay -rtsp_transport tcp -fflags nobuffer -flags low_delay \
  -framedrop rtsp://192.168.234.1:8554/test
```

按 `q` 退出。这一步用于查看相机图像，不运行步态或发射程序。官方视频文档首例有 `192.168.133.1`，后续例子是 `192.168.234.1`，且明确要求按实际网络修改；不要把任一示例当成所有机器的固定相机地址。若 SDK 主控和相机服务在不同地址，需以实际设备配置为准。

能播放视频只是链路通过。后续定位还需测端到端延迟、识别停更/重连，不能将 `cap.read()` 返回时间当成真实拍摄时间来通过现有 0.15 秒门槛。

## 6. 目前不能直接运行什么

`run_official_task3.sh` 和 `accept_official_ubuntu.sh` 仍是仿真入口，会启动本地官方 `robot_mujoco`、`mc_ctrl` 与状态桥，并用渲染画面和射线裁判完成任务。它们不会直接使用机器人 RTSP，也没有连接实物发射器。不要把仿真状态桥当成实物反馈，或将本地仿真控制器替换进机器人原有系统。

官方原版 `demo/zsl-1/python/examples/highlevel_demo.py` 包含站立、持续走动、跳跃、前跳、后空翻等动作，不能拿完整示例作为首次只读网络检查。保留官方示例原样，后续另建受限的实物探测入口。即便只读取 SDK，初始化后也需按官方设备的控制权和失联行为安排测试，不能把 SDK 客户端当成完全无影响的普通 SSH 连接。

官方 FAQ 明确：SDK 运行时优先级高于手柄，手柄不能同时切换接管；连续约三秒未接收 SDK 数据会进入阻尼趴下。开始有动力的测试前，应确认设备急停/停机方式、支撑条件与电量；不要把关闭程序或普通手柄接管当成已经验证的独立急停。

## 7. 从联网到任务三实物的推荐顺序

1. **首次联网**：SSH 可登录、知道两端实际 IP、查看设备型号/固件版本和原网络配置、真实视频能播放。
2. **独立只读探测**：新硬件入口加载架构匹配的官方 SDK，只记录连接、模式、姿态、电量和实际相机图像；不自动站立、转向或发射。当前 Python 绑定为 CPython 3.10，笔记本用 x86_64 库，ARM 机载板用 aarch64 库。
3. **反馈与图像可信性**：向厂家确认实机状态采样序号/时间戳或同源采集心跳，以及视频采集时刻、时钟映射；官方 getter 调用时刻不能替代源数据时间。确认失联、掉帧与重连时旧授权会撤销。
4. **标定与静态视觉**：标定真实相机 K、畸变、相机到机体和发射器到机体外参，测量 Tag 实际边长和 Tag 到靶心偏移。真实 Tag 图像仅显示 ID、位姿和误差；不能直接沿用仿真 960×720、fx=fy=650 或外参。
5. **受限动作**：核对实机固件、策略和姿态接口的实际响应、符号、增益，再逐步验证站立、停稳、小角度转向和单靶瞄准。当前 PI 响应配置只对所附仿真策略验证过；单个 SDK 接口相同不等于实物参数已经标定。
6. **真实射击**：接入发射器实际协议、发射确认、忙碌/超时、幂等发次和弹药反馈；从单靶一发验证，再进入三方向和五发巡回。保留默认基础三发和裁判确认的预算规则；本轮没有实现上一任务弹药导入。

可复用现有任务状态机、目标身份映射、巡回顺序和逐发账本，并通过新硬件后端替换模拟相机、模拟反馈与射线发射器。实物命中、裁判得分须来自实际比赛反馈，仿真射线的 50 分不能作为实物成绩。
